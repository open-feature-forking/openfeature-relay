# Requirements: OpenFeature Relay

Derived from [vision.md](vision.md). Terms follow [glossary.md](glossary.md).

## Functional Requirements

| ID     | Title                          | User Story                                                                                                                                                                              | Priority | Status   |
|--------|--------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------|----------|
| FR-001 | Define Manifest                | As a Distribution Builder, I want to describe a distribution in a YAML manifest so that its contents are declared, reviewable and versioned.                                           | High     | Verified |
| FR-002 | Select Components              | As a Distribution Builder, I want to list sync providers, configuration formats, evaluators, service endpoints, event sinks, telemetry providers and middleware in the manifest, and optionally the module that provides the command line, so that only those are compiled in. | High     | Verified |
| FR-003 | Reference Component Modules    | As a Distribution Builder, I want to reference each component by Go module path and version so that official and third-party components are selected the same way.                  | High     | Verified    |
| FR-004 | Validate Manifest              | As a Distribution Builder, I want the builder to reject an invalid manifest with an error naming the faulty entry so that I fix it before anything is generated.                    | High     | Verified |
| FR-005 | Generate Distribution Source   | As a Distribution Builder, I want the builder to generate the distribution's Go source and go.mod from the manifest so that I can inspect or commit the result.                       | High     | Verified |
| FR-006 | Compile Distribution           | As a Distribution Builder, I want the builder to compile the generated source into a flagd binary so that one command produces a runnable distribution.                              | High     | Verified |
| FR-007 | Skip Build Steps               | As a Distribution Builder, I want to skip the generate, module resolution or compile step so that I can plug the builder into my own build pipeline.                                 | Medium   | Verified |
| FR-008 | Replace Modules Locally        | As a Distribution Builder, I want to declare module replacements in the manifest so that I can build against a local checkout of a component.                                       | Medium   | Verified    |
| FR-009 | Build Container Image          | As a Distribution Builder, I want a reference Dockerfile for a built distribution so that I can ship it as an image the same way flagd ships today.                                  | Low      | Implemented |
| FR-010 | Write Custom Sync Provider     | As an Extension Author, I want to implement a sync provider behind the sync factory interface in my own module so that flagd reads flags from a source it does not support.          | High     | Verified    |
| FR-011 | Write Custom Service Endpoint  | As an Extension Author, I want to implement a service endpoint behind the service factory interface in my own module so that flagd serves flags over a protocol it does not support. | High     | Verified    |
| FR-012 | Write Custom Middleware        | As an Extension Author, I want to implement HTTP middleware behind the middleware factory interface so that I can add cross-cutting behaviour such as authentication or rate limits.  | Medium   | Verified    |
| FR-013 | Write Custom Telemetry         | As an Extension Author, I want to implement a telemetry provider behind the telemetry factory interface so that flagd reports to a backend other than OpenTelemetry.                 | Medium   | Verified    |
| FR-014 | Write Custom Evaluator         | As an Extension Author, I want to implement an evaluator that resolves one, several or all flags of a selector for an evaluation context and returns untyped results, so that flagd evaluates flags with another engine, such as the Flagsmith engine or GO Feature Flag's evaluation module, while type checks stay in the core. | Medium   | Implemented |
| FR-015 | Test Component Against Contract| As an Extension Author, I want reusable contract tests for each component type so that I know my component behaves as flagd expects before I build it in.                         | Medium   | Verified    |
| FR-016 | React to Runtime Events        | As an Extension Author, I want my service endpoint to subscribe to runtime events through the event bus so that it reacts to flag changes without the runtime knowing its type.    | High     | Verified    |
| FR-017 | Combine Service Endpoints    | As a Distribution Builder, I want to select any combination of service endpoints, from OFREP alone or flag evaluation alone to all of them plus extensions, so that the distribution exposes exactly the access I need. | High     | Implemented |
| FR-018 | Check Component Dependencies   | As a Distribution Builder, I want the builder to reject a manifest whose components need a component it does not select, such as OFREP without an evaluator or an evaluator without its configuration format, so that every distribution I build can start. | High     | Implemented |
| FR-019 | Write Configuration Format     | As an Extension Author, I want to implement a configuration format that validates another vendor's flag configurations and reports each document's flag keys, flag set, version and changes so that the store, routing, event streams, a configuration proxy and my evaluator all work with that format. | Medium   | Implemented |
| FR-020 | Run Full Distribution          | As an Operator, I want to run flagd-full with my existing flags, configuration file, environment variables and ports so that upgrading needs no change on my side.                  | High     | Verified |
| FR-021 | Use Standard Distribution      | As an Operator, I want to pick a standard distribution (minimal, minimal with OpenTelemetry, cloud, Kubernetes, sync, full) as a binary or image so that I get a smaller flagd without running the builder.          | High     | Verified |
| FR-022 | Fail on Unavailable Scheme     | As an Operator, I want flagd to fail at startup with the list of available schemes when a source uses a scheme not in the distribution so that a wrong distribution is obvious.    | High     | Implemented |
| FR-023 | List Components                | As an Operator, I want a `flagd components` command that lists the components compiled into the binary, as text or JSON, so that I and my tooling know what a distribution supports.                    | Medium   | Verified |
| FR-024 | Run Without Telemetry          | As an Operator, I want a distribution with the noop telemetry provider so that flagd carries no observability code or overhead when I do not need it.                              | Medium   | Verified    |
| FR-025 | Run Configuration Proxy        | As an Operator, I want to run a distribution with sync providers and the flag sync endpoint but no evaluator so that in-process providers receive their flag configurations from one place without flagd evaluating anything. | High     | Implemented |
| FR-026 | Validate Without Evaluator     | As an Operator, I want a configuration proxy to reject invalid flag configurations the same way flagd-full does so that in-process providers never receive a configuration flagd-full would refuse.                  | High     | Implemented |
| FR-027 | Serve Vendor Flags             | As an Operator, I want to run a distribution built from another vendor's sync provider, configuration format and evaluator behind OFREP so that flagd can replace that vendor's own edge proxy.            | Low      | Implemented     |
| FR-028 | Supply Source Credentials      | As an Operator, I want to pass credentials for a source, such as a vendor API key, through environment variables or files so that secrets never appear in a manifest or on the command line.                | High     | Implemented |
| FR-029 | Name Source Format             | As an Operator, I want to name the configuration format of a source, with flagd's format as the default, so that one distribution reads flagd and vendor flag configurations side by side.          | Medium   | Implemented |
| FR-030 | Publish Standard Distributions | As a Maintainer, I want each flagd release to publish the standard distributions' manifests, binaries and images so that Operators can use them directly.                           | High     | Implemented     |
| FR-031 | Release Component Modules      | As a Maintainer, I want each component module to be tagged and released so that manifests can pin component versions.                                                              | High     | Implemented     |
| FR-032 | Build Distributions in CI      | As a Maintainer, I want CI to build every standard distribution, run the test-harness suites against flagd-full and check NFR-001, NFR-004, NFR-005, NFR-011 and FR-026 so that a change that breaks compatibility or a dependency boundary fails the build. | High     | Verified   |
| FR-033 | Trace Evaluations              | As an Operator, I want the flag evaluation and OFREP service endpoints to record one evaluation span per evaluation request, a bulk request included, whenever the distribution has an OpenTelemetry telemetry provider so that flagd-full keeps today's traces and other distributions trace the same way. | Medium   | Verified    |
| FR-034 | Show Distribution Identity     | As an Operator, I want `flagd version --verbose` to name the distribution and its manifest version so that I can tell which distribution is running.                                                       | Medium   | Verified |
| FR-035 | Evaluate Formats Side by Side  | As an Operator, I want the flag evaluation and OFREP service endpoints to resolve each flag of a request's selector with the evaluator of the configuration format that holds it, following today's source precedence for a key held twice within that selector, so that flagd and vendor flags are served by one distribution. | Medium   | Implemented |
| FR-036 | Write Custom Event Sink        | As an Extension Author, I want to implement an event sink behind the event sink factory interface in my own module so that flagd delivers configuration change, evaluation or tracking events to a system it does not support, such as a vendor's analytics API. | Medium   | Verified    |
| FR-037 | Export Evaluation Events       | As an Operator, I want the flag evaluation and OFREP service endpoints to publish an evaluation event per resolved flag to the event sinks the distribution selects so that experimentation and analytics see every evaluation flagd serves. | Medium   | Verified        |
| FR-038 | Notify Configuration Changes   | As an Operator, I want event sinks to receive a configuration change event naming the source, flag set, added, updated and removed flag keys whenever a configuration format accepts a changed document so that people and systems learn about flag changes. | Medium   | Verified        |
| FR-039 | Collect Provider Events        | As an Operator, I want a service endpoint that accepts evaluation and tracking events from in-process providers and publishes them on the event bus so that in-process evaluations reach the same event sinks as remote ones. | Low      | Verified        |
| FR-040 | Embed Evaluator                | As a Provider Author, I want to import the evaluator and the flagd configuration format modules without telemetry, transport or sync-implementation dependencies so that my provider stays small and hook-observable. | High     | Implemented |
| FR-041 | Evaluate Like flagd            | As a Provider Author, I want the embedded evaluator to be the same code flagd evaluates with so that in-process and remote evaluation return identical results.                     | High     | Implemented |
| FR-042 | Reuse Single Sync Provider     | As a Provider Author, I want to import one sync provider module without the others so that my provider only pulls in the sources it supports.                                       | Medium   | Implemented |
| FR-044 | Request Configuration Format   | As a Provider Author, I want my provider's flag sync request to name the configuration format it reads, flagd's being the default, so that it only receives documents it can parse and existing providers keep working unchanged. | Medium   | Implemented |
| FR-045 | Write Fetcher                  | As an Extension Author, I want to implement a sync provider as a fetcher, a function that fetches a source on request with conditional requests, so that the core decides when to fetch and I write only the vendor-specific request. | High     | Verified    |
| FR-046 | Stream Configuration Changes   | As an Operator, I want the OFREP service endpoint to advertise and serve an event stream and answer bulk requests with ETags for every configuration format so that OFREP clients refresh only when the flags of their selector change. | Medium   | Implemented |
| FR-047 | Derive Selector From Credential| As an Operator, I want middleware to bind a request to a selector and to request attributes derived from its credential so that one distribution serves several environments or flag sets, each to its own clients. | Medium   | Implemented |
| FR-048 | Ship Engine Module             | As an Extension Author, I want to provide a configuration format and its paired evaluator from one component module so that a vendor engine that holds both can be built in unchanged. | High     | Implemented |
| FR-049 | Decode Common Encodings        | As an Extension Author, I want the core to decode JSON and YAML flag configurations before my configuration format sees them so that my format handles only its schema. | Low      | Verified    |
| FR-050 | Persist Snapshot               | As an Operator, I want flagd to persist the current flag state to a local snapshot on every change so that a restart has data even when the upstream source is down.              | Medium   | Deferred |
| FR-051 | Bootstrap From Snapshot        | As an Operator, I want flagd to load the snapshot as the lowest-precedence source at startup so that it serves flags immediately and live data overrides them once available.      | Medium   | Deferred |
| FR-052 | Report Stale Sources           | As an Operator, I want readiness to fail when a source has not been reached within a configured age so that a load balancer stops routing to a flagd serving outdated flags. | Low      | In Progress |
| FR-053 | Combine Fetch Triggers         | As an Operator, I want to attach one or more fetch triggers to a fetcher's source (an interval, a server-sent event stream, a file watch, a webhook) so that flagd refetches as soon as the source changes and still polls as a fallback. | High     | Verified    |
| FR-054 | Write Fetch Trigger            | As an Extension Author, I want to implement a fetch trigger behind the trigger factory interface, such as a vendor's change event stream, so that a fetcher refetches on that vendor's signal without changing the fetcher. | Medium   | Verified    |
| FR-055 | Write Streaming Sync Provider  | As an Extension Author, I want to implement a sync provider that both detects changes and delivers flag configurations, as flagd's gRPC sync protocol and the OpenFeature Operator do, so that push protocols keep working without a separate fetcher. | High     | Verified    |
| FR-056 | Provide Testbed Control API    | As a Provider Author, I want a launchpad-compatible control API as a reusable module so that my provider's test suites, and other testbeds, can start, stop, restart and change a flagd without changing the suites. | High     | Implemented |
| FR-057 | Simulate Outages and Restarts  | As a Provider Author, I want a testbed outage to close the runtime's listeners and every start to reload a cleaned store so that my provider sees refused connections, broken streams and fresh flags as against a restarted flagd. | High     | Implemented |
| FR-058 | Retry Upstream Sync Like the Provider | As an Operator, I want a `grpc` source to opt into the Go flagd provider's retry policy and reconnect delay so that it survives the upstream's outages the way the providers do. | Medium | Verified |
| FR-059 | End on Fatal Sync Status         | As an Operator, I want a `grpc` source to opt into status codes that end flagd before the source's first payload so that a wrong credential fails the start instead of retrying forever. | Medium | Verified |
| FR-060 | Recycle and Keep Alive Upstream Sync | As an Operator, I want a `grpc` source to opt into a stream deadline, HTTP/2 keepalive and readiness on its first payload so that long-lived streams survive intermediaries and the sync provider's readiness means a payload arrived. | Medium | Verified |
| FR-061 | Send Selector as Header          | As an Operator, I want a `grpc` source to opt into sending its selector as the `flagd-selector` header so that an upstream that prefers the header sees the selector. | Medium | Verified |
| FR-062 | Resolve Headers From Secrets     | As an Operator, I want a `grpc` source to resolve `headersFrom` like every other source so that its credentials come from the environment or a file. | Medium | Verified |
| FR-063 | Select Deprecated Flag Evaluation Services | As a Distribution Builder, I want the deprecated `schema.v1` and `flagd.evaluation.v1` flag evaluation services as their own component that the flag evaluation endpoint serves on its port, so that a distribution serves them only when its manifest lists it. | Medium | Verified |

## Non-Functional Requirements

| ID      | Title                         | Requirement                                                                                                                                                                                      | Category        | Priority | Status |
|---------|-------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------|----------|--------|
| NFR-001 | Evaluation Performance        | No evaluator benchmark (`make flagd-benchmark-test`) increases allocs/op over the pull request's base commit; ns/op within 5% of that baseline is reported, not gating, on shared CI runners. | Performance     | High     | Verified    |
| NFR-002 | Startup Time                  | flagd-full reaches readiness within 10% of the time today's flagd needs with the same sources, measured over 10 runs.                                                                          | Performance     | Medium   | Verified |
| NFR-003 | Minimal Distribution Size     | The flagd-minimal binary is at most 50% of the size of the flagd-full binary for the same OS and architecture.                                                                               | Portability     | High     | Verified |
| NFR-004 | Minimal Distribution Deps     | The flagd-minimal binary links no module under `k8s.io`, `cloud.google.com`, `github.com/aws`, `github.com/Azure` or `go.opentelemetry.io/otel/sdk`, and the packages of the distribution import none.                              | Maintainability | High     | Verified   |
| NFR-005 | Evaluator Dependency Boundary | `go list -deps` of the evaluator module and of the flagd configuration format module lists no package under `go.opentelemetry.io`, `google.golang.org/grpc`, `connectrpc.com`, `k8s.io` or `gocloud.dev`, enforced in CI. | Maintainability | High     | Implemented |
| NFR-006 | Core Dependency Boundary      | The core module depends only on the Go standard library and the modules its data types need; it has no dependency on gRPC, ConnectRPC, OpenTelemetry or any cloud SDK.                    | Maintainability | High     | Verified    |
| NFR-007 | Compatibility Verification    | flagd-full passes the flagd test-harness RPC and in-process suites with the same tag selection and results as today's flagd.                                                                  | Maintainability | High     | Verified   |
| NFR-008 | Build Duration                | Generating and compiling flagd-full with a warm module cache takes at most 3 minutes on a GitHub-hosted `ubuntu-latest` runner.                                                               | Performance     | Low      | Verified |
| NFR-009 | Platform Matrix               | Every standard distribution builds for the same OS and architecture matrix flagd releases today, and its images for `linux/amd64` and `linux/arm64`.                                         | Portability     | High     | Implemented |
| NFR-010 | Example Components            | Each factory interface has an example component in the repository that CI builds into a distribution and starts successfully.                                                                | Usability       | Medium   | Verified |
| NFR-011 | Proxy Distribution Deps       | The flagd-sync binary links no evaluator module and no `github.com/diegoholiveira/jsonlogic` module, and the packages of the distribution import none.                                                                                 | Maintainability | High     | Implemented |
| NFR-012 | Stable Dependencies           | No Go file imports `golang.org/x/exp` or another experimental package once the Go standard library offers an equivalent (`maps`, `slices`, `cmp`, `iter`), and no go.mod requires one directly; indirect requirements through third-party modules are allowed. | Maintainability | Medium   | Verified |
| NFR-013 | Event Publishing Overhead     | With no event sink selected, publishing evaluation events adds no allocation to the endpoint benchmarks of the flag evaluation and OFREP service endpoints (the evaluator publishes nothing); with sinks selected, a full sink buffer drops events and counts the drops instead of blocking evaluation. | Performance     | High     | Verified      |
| NFR-014 | Drop-In Testbed               | Provider suites that pass against the flagd-testbed image run unchanged against the relay testbed and pass the same scenarios. | Compatibility   | High     | Implemented |
| NFR-015 | Test-Only Components          | No standard distribution manifest contains a module under `testbed/`. | Maintainability | Medium   | Implemented |
| NFR-016 | Drop-In Upstream Sync         | Without a `grpc` object, a `grpc` source behaves as before: the same schedule, fail-fast connection, retries, keepalive, dial options and request metadata. | Compatibility   | High     | Verified |
| NFR-017 | Correct Under Concurrent Load | Under concurrent OFREP, flag evaluation and flag sync clients, while its flags change, flagd-minimal answers every request from a flag generation inside the change window (one written between the apply bound before the request and the moment the answer returns), delivers to every flag sync stream and every flag evaluation `EventStream` every flag generation written while it is connected (a stream that lags more than one change interval fails), and shows no data race. Proven by `make test-load` (gated in CI) and `make test-load-smoke` (every build). | Reliability | High     | Verified |

## Constraints

| ID    | Title                     | Constraint                                                                                                                                                 | Category    | Source                      | Priority | Status |
|-------|---------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------|-----------------------------|----------|--------|
| C-001 | Standard Go Tooling       | Distributions are built with Go modules and `go build`; no Go plugins, no dynamic linking, no custom package manager.                                    | Technical   |                             | High     | Verified    |
| C-002 | Go Version                | Modules target the Go version flagd's modules declare (core: Go 1.26).                                                                                    | Technical   |                             | High     | Open   |
| C-003 | Full Distribution Compat  | flagd-full keeps today's CLI flags, configuration file format, environment variables, ports, endpoints and image name `ghcr.io/open-feature/flagd`.     | Technical   |                             | High     | Implemented |
| C-004 | Go Import Paths May Move  | Go import paths under `core/` may change.           | Technical   |                             | High     | Open   |
| C-005 | Protobuf Package Layout   | The generated protobuf package layout, including its `openfeature/` nesting, stays unchanged.                                                            | Technical   |                             | High     | Implemented |
| C-006 | Upstream Delivery         | Work lands in `open-feature/flagd` as incremental pull requests opened from `open-feature-forking/flagd`; OpenFeature Relay stays rebased on upstream main. | Business    |                             | High     | Open   |
| C-007 | License                   | All code is licensed under Apache License 2.0.                                                                                                            | Regulatory  | Apache License 2.0          | High     | Open   |
| C-008 | Developer Certificate     | Every commit carries a DCO sign-off.                                                                                                                      | Regulatory  | Developer Certificate of Origin 1.1 | High | Open |
| C-009 | FIPS Build                | The relay's releases and images ship no FIPS 140-3 build. Anyone can produce a FIPS 140-3 build of any distribution with the builder, with the same crypto boundary as today's FIPS build; it is documented, not verified in CI. | Regulatory  | FIPS 140-3; docs/reference/fips-140-3.md | High | Implemented |
| C-010 | Acceptance Suite          | The flagd test-harness Gherkin suites remain the acceptance suite for evaluation and sync behaviour.                                                    | Operational |                             | High     | Implemented |
| C-011 | Release Tooling           | Releases keep using conventional commits and release-please.                                                                                             | Operational |                             | Medium   | Implemented   |
