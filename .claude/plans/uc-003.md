## 0. Spec questions and recommendations

Each needs the project lead's decision before implementation. The recommendation comes first.

- **Q1, the fetcher's version is not a document version.** UC-003 step 3, BR-004 and UC-008's Fetcher row say a fetcher returns a "document version". The glossary defines Document Version as what a *configuration format* reports per flag set; a fetcher sees the whole flag configuration of a source before any format has parsed it, and it may hold several flag sets.
  - **Recommendation:** add the glossary term **Source Version**: an opaque value a fetcher returns for a source's flag configuration as read (an ETag, a content hash, a modification time), handed back on the next fetch. Use it in UC-003 step 3, BR-004 and UC-008's Fetcher row.
- **Q2, a failed first fetch stops flagd today.** `http.Sync.Sync` and `blob.Sync.Sync` return the initial fetch's error, so the runtime's errgroup exits flagd. BR-008 says a recoverable source error never stops flagd.
  - **Recommendation:** follow BR-008. The fetching sync provider stays up, not ready, and the poller retries with backoff. It is a behaviour change for flagd-full (an unreachable source at startup no longer restarts the pod, readiness fails instead); C-003 names CLI, configuration, ports and endpoints, not this. List it in the PR description and the UC-009 migration notes.
  - *Alternative:* keep exit-on-first-failure as an option of the fetching sync provider, on in flagd-full.
- **Q3, the poller's backoff.** The glossary gives the core's poller "jitter and backoff"; today's poller has a deterministic seed offset (`intervalSeed`) and no backoff.
  - **Recommendation:** after a failed fetch, the next poll waits `interval × 2^n`, capped at `max(interval, 60s)`, and resets on the first success. A 5 s source retries at 5, 10, 20, 40, 60 s; a source with an interval of 60 s or more never polls less often than configured. The seed offset stays as the jitter; no random jitter is added.
- **Q4, a missing or empty file.** Today the file provider delivers `{}` whenever the read fails or the file is empty, which removes all of the source's flags. BR-004 says a failed fetch delivers nothing.
  - **Recommendation:** a file that does not exist or is empty is a successful fetch of an empty flag configuration (`{}`), as today. Any other read error, such as a permission error, becomes a failed fetch that keeps the previous flags. That is a small, safer behaviour change, pinned by a characterization test first and then changed in its own commit.
- **Q5, the operator's FeatureFlag resource is reshaped (gap from UC-018 BR-003).** `ofoperator` converts the resource to the operator's Go type and delivers `json.Marshal(ff.Spec.FlagSpec)`. BR-010 says a sync provider never transforms a flag configuration.
  - **Recommendation (a):** amend UC-003 BR-010. A sync provider may take the flag configuration out of its source's protocol envelope (the `flagConfiguration` field of a flagd sync message, the `spec.flagSpec` of a FeatureFlag resource), but it never changes that flag configuration. The operator provider keeps today's typed conversion, so flagd-full does not change. That closes the gap by a spec change, not by code.
  - *Alternative (b):* deliver the whole resource and add an `openfeature-operator` configuration format that unwraps it. That is cleaner in principle, but flagd-proxy and the flag sync endpoint would send in-process providers documents they cannot parse until UC-017's format selection lands. Not PoC-sized.
- **Q6, how an Operator attaches fetch triggers (FR-053, A2).** Without a configuration surface, no extension fetch trigger can be used.
  - **Recommendation:** `SourceConfig` gains an optional `triggers` list, `[{"type": "<trigger type>", ...settings}]`. If it is absent, a source gets today's triggers: the poller for `http`, `gcs`, `azblob` and `s3`, and the file watch for `file`, with fsnotify inside Kubernetes and fileinfo outside it. `interval` and `intervalSeed` keep configuring the poller. The provider names `fsnotify` and `fileinfo` stay as aliases for `file` with that trigger. Only additions; nothing existing changes (C-003).
- **Q7, per-cloud module graphs (gap from UC-014 Q14 and the azblob leak).** gocloud.dev is one module that requires all three cloud SDKs. Its shared internals also put Google API client libraries into azblob's package graph: `gocloud.dev/internal/useragent` imports `google.golang.org/api/option` and `google.golang.org/grpc`, and `gocloud.dev/internal/retry` imports `github.com/googleapis/gax-go/v2` (checked with `go list -deps` on the ref).
  - **Recommendation:** rewrite the three blob fetchers on native SDK clients in UC-003's last PR (PR 5): `cloud.google.com/go/storage`, `github.com/Azure/azure-sdk-for-go/sdk/storage/azblob`, and `github.com/aws/aws-sdk-go-v2/service/s3`. Credentials come from each SDK's default chain, as gocloud uses them.
  - The compatibility surface is gocloud's URL query options. Support exactly the options gocloud documents per driver (characterized in PR 1); an unknown option fails at startup and names the option.
  - *Alternative:* keep gocloud and move the gap to UC-010, since no NFR demands per-cloud graphs (NFR-004 excludes every cloud from flagd-minimal anyway). PR 5 is independent of PRs 2–4 and can be dropped without changing UC-003's status.
- **Q8, staleness (FR-052, second half of BR-005).** This is runtime readiness and needs a new flag.
  - **Recommendation:** an accepted gap owned by UC-004 (runtime registry, phase 3). FR-052 stays Open.
- **Q9, decoding in the core (BR-010, FR-049).** Today every fetcher calls `utils.ConvertToJSON`.
  - **Recommendation:** a fetcher returns the bytes as read plus an encoding hint (file extension, content type), and the core's fetching sync provider decodes them. That meets BR-010 for fetchers at no extra cost. Streaming sync providers keep delivering JSON text. TOML stays out (the FR-049 gap from UC-018 stays as written).
- **Q10, example components (UC-008 BR-005, NFR-010).** There are three factory interfaces.
  - **Recommendation:** `test/sync-example` has two parts: an example fetcher for an `example://` scheme that reads from an in-memory source the test changes, and an example fetch trigger that signals on `SIGHUP`. The streaming example is the official `flagd-grpc` provider, which runs the streaming contract. Building them into a distribution and starting it (NFR-010) is UC-001.

## 5. Risks

- **C-003, timing and duplicates.** Single-flight fetching, file dedupe (BR-004), backoff (Q3) and staying up on a failed first fetch (Q2) change what an Operator observes in failure cases, not in the happy path. Each change is its own commit with an updated characterization row and a line in the PR description.
- **C-003, source names.** Readiness and the `Formats` map are keyed by the name a delivery carries. Blob delivers `bloburi.Join(...)`, not the configured URI. The factory returns the name explicitly (2b), and `TestSourceMappingCharacterization` pins it.
- **C-003, metrics.** The fetching sync provider records instead of each provider. The metrics type is passed in explicitly, so all three clouds keep `blob`; the extended metrics characterization guards this.
- **C-003, cloud options (PR 5).** Native SDKs do not read gocloud's query options. Q7 limits PR 5 to the characterized options, with unknown options failing loudly. Credentials use each SDK's default chain, which is what gocloud uses underneath. If MinIO or Azurite cannot run in CI, 5b and 5c stay `-short`-skipped and the reviewer runs them locally.
- **NFR-006.** The core gains interfaces, the fetching sync provider and the contract runners. `synctest` uses only `testing` and the standard library, and the core graph gate pins this.
- **BR-001.** Today the per-cloud modules depend on `sync/blob`, another flagd module. PR 5 removes it. Until then it is a shared library, not a selectable component, and is listed as such.
- **C-004.** `ISync` → `StreamingSyncProvider` keeps an alias, so flagd-proxy and in-process providers need no change in this slice. `NewHTTP`, `NewFileSync` and the exported blob fields go away (C-004 allows it; FR-043's migration guide lists them, UC-015).
- **C-005.** No protobuf change.
- **Over-building.** No runtime registry or event bus (UC-004), no manifest or builder (UC-001), no staleness (UC-004), no SSE, webhook or vendor triggers, and no telemetry factory (UC-006).
