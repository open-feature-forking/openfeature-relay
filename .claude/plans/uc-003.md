## 0. Spec questions and recommendations

Each question needs the project lead's decision before implementation. The recommendation comes first.

- **Q1, the fetcher's version is not a document version.** UC-003 step 3, BR-004 and UC-008's Fetcher row say "document version". The glossary gives that term to the configuration format, per flag set.
  - **Recommendation:** add the glossary term **Source Version**: an opaque value a fetcher returns for its source's flag configuration as read (an ETag, a content hash, a generation), handed back on the next fetch. Use it in those three places. In code it is a plain `string`.
- **Q2, failure policy for every sync provider.** Today a failed first fetch stops flagd for `http`, `blob` and `openfeature-operator`, and so does a failed first `SyncFlags` call for `flagd-grpc`, because their `Sync` returns the error into the runtime's errgroup. Once ready, every official provider stays ready through source outages: gRPC sets `ready` on each stream open and never clears it, and the operator provider never clears it either. BR-008 says a recoverable error never stops flagd, and a streaming sync provider "reports itself not ready" while reconnecting.
  - **Recommendation, part 1:** a failed first fetch or connect never stops flagd. The provider stays up and not ready, and retries by itself with Q3's backoff, whatever triggers are attached. This changes flagd-full: an unreachable source at startup no longer restarts the pod, readiness fails instead. It goes into the PR description and UC-009's migration notes. A path that does not exist at startup is a configuration error and still fails fast (Q4).
  - **Recommendation, part 2:** amend BR-008 so that a sync provider that loses its source after a first delivery reconnects and **stays ready** with its last accepted flag configuration. Readiness is then lost only through staleness (BR-005, FR-052). That is today's behaviour for every official provider, so C-003 holds. It also avoids a sync-relay outage taking every flagd pod out of service while each still holds valid flags.
  - *Alternative to part 2:* implement BR-008 as written, so pods go not ready during source outages. That changes C-003 readiness.
- **Q3, the poller's backoff, jitter and alignment.** The glossary gives the core's poller "jitter and backoff". Today the poller has only the deterministic `intervalSeed` offset, which is 0 without a seed, and no backoff.
  - **Recommendation:**
    - The happy path is unchanged: polls stay aligned to `OffsetSchedule`.
    - After the first failed fetch, the next poll keeps its normal schedule.
    - From the second consecutive failure, the wait is `min(interval × 2^(n−1), cap)` plus a random jitter in `[0, wait/2)`, measured from the failure. The cap is `max(interval, 60 s)`.
    - The first success returns to the aligned schedule.
    - The same policy drives the first-fetch retries of Q2 and the restarts of a failing fetch trigger (step 2a).
- **Q4, missing, empty and unreadable files.**
  - **Recommendation:** keep three cases apart.
    - **Missing at startup:** today flagd fails because `Init` adds a watch on a missing path. Keep that, through the file fetcher's `Init`, which checks that the path exists.
    - **Deleted later, or empty:** a successful fetch of an empty flag configuration, `{}`, as today.
    - **Any other read error,** such as a permission error: today it delivers `{}` and wipes the source's flags. It becomes a failed fetch that keeps the previous flags. That is a behaviour change, listed with Q2.
  - The file watch trigger also signals on chmod, so a fixed permission is picked up.
- **Q5, the operator reshapes the FeatureFlag resource (the gap UC-018 BR-003 assigns to UC-003).** `ofoperator` converts the resource into the operator's Go type and delivers `json.Marshal(ff.Spec.FlagSpec)`. That round trip drops fields the Go type does not define (`$schema`, unknown flag-level keys) and reorders keys.
  - **Recommendation (c):** deliver `spec.flagSpec` from the unstructured object (`unstructured.NestedFieldNoCopy`, then `json.Marshal`), so the flag configuration reaches flagd's configuration format as written in the resource. Amend BR-010 so that a sync provider may take the flag configuration out of its source's protocol envelope (the `flagConfiguration` field of a flagd sync message, the `spec.flagSpec` of a FeatureFlag) but never changes it. flagd's format only warns on schema violations (UC-018 Q2), so the change can add warnings but cannot reject a resource that is accepted today. PR 1 pins today's output for a resource with `$schema` and an unknown flag-level field; PR 3 changes it in its own commit, listed as a behaviour change. The gap closes.
  - *Alternative (a′):* keep the typed conversion and word the amendment as what the code does ("takes `spec.flagSpec` as the operator's typed FlagSpec; fields outside that type are not delivered"). The gap then stays listed in UC-003 and UC-018 with no owner.
- **Q6, how an Operator attaches fetch triggers, and how extension schemes reach `--uri` (FR-053, BR-002, step 8).**
  - **Recommendation:** two additions, nothing removed (C-003).
    - `SourceConfig` gains an optional `triggers` list, `[{"type": "<trigger type>", ...settings}]`. When it is absent, a fetcher's source gets its factory's default triggers, and the core's poller when the factory declares none (UC-003 step 8). That gives today's triggers for the official fetchers: the poller for `http`, `gcs`, `azblob` and `s3`, and the file watch for `file` (fsnotify inside Kubernetes, fileinfo outside), and the poller for an extension fetcher. `interval` and `intervalSeed` keep configuring the poller. *(Revision 3 spells out the extension case the approved recommendation left implicit; the decision is unchanged.)*
    - Every fetcher and streaming factory parses the URIs of its own schemes (`ParseURI(uri) (SourceConfig, bool)`), so `--uri example://…` selects an extension exactly like an official scheme. Official factories reproduce today's rewriting: `file:` and `core.openfeature.dev/` stripped, `grpcs://` stripped with TLS on, the custom resolver prefixes kept.
    - The provider names `fsnotify` and `fileinfo` stay as aliases for `file` with that trigger.
- **Q7, per-cloud module graphs (the UC-014 Q14 gap and the azblob package leak).**
  - **Recommendation:** native SDK fetchers in PR 5, keeping the whole documented configuration surface. Section 3 lists it per cloud: gocloud v0.42.0's URL options for S3 and GCS, and its Azure environment variables, which `docs/concepts/syncs.md` points users to. Each item gets an `httptest` stub test that runs under `-short` in CI.
  - *Alternative:* keep gocloud and move the gap to UC-010. No NFR demands per-cloud graphs; NFR-004 already keeps every cloud out of flagd-minimal. PR 5 is independent of PR 4 and can be dropped without changing UC-003's status.
- **Q8, staleness (FR-052, the second half of BR-005).** Staleness is runtime readiness and needs a new flag.
  - **Recommendation:** an accepted gap owned by UC-004 (runtime registry, phase 3). With Q2 part 2 it becomes the only way an outage affects readiness.
- **Q9, decoding moves into the core (BR-010, FR-049).**
  - **Recommendation:** a fetcher returns the bytes it read with the file extension and content type; the core's fetching sync provider decodes them through `utils.ConvertToJSON`. Streaming sync providers keep delivering JSON text. TOML stays out (UC-018's FR-049 gap is unchanged).
- **Q10, example components (UC-008 BR-005, NFR-010).**
  - **Recommendation:** `test/sync-example` holds an `example://` fetcher that reads an in-memory source the test changes, and a fetch trigger that signals on `SIGHUP`. The streaming example is the official `flagd-grpc` provider. Building them into a distribution and starting it (NFR-010) is UC-001.
- **Q11 (new in revision 3), what a deleted FeatureFlag resource delivers.** The spec does not say. Today the operator provider logs the delete event and delivers nothing, so the last flags stay in force. A deleted file delivers `{}` (Q4, approved), which removes them.
  - **Recommendation:** keep today's behaviour and state it in UC-003, under a new rule for sources that disappear: a deleted file is an empty flag configuration, and a deleted FeatureFlag resource delivers nothing and keeps the last accepted flags. `RunStreaming` gets a "source removed" case whose expected behaviour the factory's test inputs declare (`OnRemove: Keep | Empty`). The operator declares `Keep`.
  - *Alternative:* a deleted resource delivers `{}`, as a file does. That is consistent, but it changes flagd-full (C-003) and is listed with Q2's changes.

## 5. Risks

- **C-003, the behaviour changes.** Each is its own commit (3g) and is listed in the PR description and UC-009's migration notes:
  - No exit on a failed first fetch or connect (Q2).
  - A file read error keeps the previous flags (Q4).
  - Unchanged file content no longer redelivers.
  - A closed file watch reconnects instead of stopping flagd.
  - The operator delivers `spec.flagSpec` as written (Q5).
  - `incrementalUpdates` is honoured for every fetcher (it is experimental and opt-in per source).
  - A default fetch deadline of `max(interval, 30 s)`.
  - Backoff after two consecutive failed polls (Q3).
  - `awssdk=v1` on an `s3://` source fails at startup (PR 5; the native client is AWS SDK v2 only).
  - File metric counts: `{}` is counted and unchanged content is not.
  - The happy path is unchanged: same schemes, provider names, `SourceConfig` fields, source names, metric names and attributes, and readiness (Q2 part 2).
- **C-003, hung fetches.** The fetching sync provider runs one fetch at a time where cron ran overlapping jobs, so a fetch without a deadline would stall the source. The default deadline and `TestFetchDeadlineUnblocksNextFetch` cover it.
- **C-003, cloud configuration (PR 5).** Native SDKs read neither gocloud's URL options nor its Azure variables. 5b–5d carry the full list from gocloud v0.42.0 with stub tests in CI. If one cannot be reproduced, PR 5 for that cloud is dropped (Q7's alternative), not shipped partially.
- **NFR-006.** The core gains interfaces, the fetching sync provider, the contract runners and `bloburi`. They use only the standard library and the core's logger, and the core rows in both boundary files pin that.
- **BR-001.** Until PR 5 the cloud modules depend on `sync/blob`, a shared library rather than a selectable component; PR 5 removes it.
- **C-004.** `ISync` stays as an alias, and `file.NewSyncProvider` gives embedders one call. The removed names are listed for UC-015.
- **C-005.** No protobuf change.
- **Over-building.** This slice adds no runtime registry or event bus (UC-004), no manifest or builder (UC-001), no staleness (UC-004), no server-sent events, webhook or vendor triggers, and no telemetry factory (UC-006).
