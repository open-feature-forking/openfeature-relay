# UC-009 plan: Upgrade to flagd-full (PoC step 9)

**Status: revision 2, approved: the project lead accepted Q1–Q13 as recommended (2026-11-04).** Revision 2 resolves `uc-009-opposer.md` (0 blockers, 5 major, 4 minor); the outcome per finding is in section 8. Issue #21. Every PR description starts with `Part of #21`.

UC-009 proves the drop-in rule (CLAUDE.md, Conventions) end to end: an Operator replaces today's flagd with a flagd-full that the Builder built from `distributions/flagd-full/manifest.yaml`, and changes nothing. It has three parts:
1. **Release from the Builder.** The `flagd` module becomes the Builder's committed output, and release archives and images come from it under today's names, tags and contents.
2. **Prove it.** A differential test runs today's flagd and the Builder-built flagd-full side by side, with the same start command, configuration file, environment, sources and requests. The test-harness suites run against the Builder-built image.
3. **Explain it.** Migration notes for Operators built from #78, with a section for embedders built from #89.

Publishing stays UC-012's: the release-please workflow stays disabled.

**Base.** `origin/main` @ fd8e973. UC-001 PR 7 (#96, `uc-001/pr-7-distributions-and-status` @ 3244cd8) brings:
- the manifest;
- `make builder-e2e`;
- the CLI and log pins against `distributions/flagd-full/build/flagd`;
- `TestGeneratedComponentsEqualHandWritten`;
- `test/distributions`.

UC-001 assigns UC-009 one gap: **flagd-full released from the generated source.**

Today, on #96's branch, every image and the test-harness run come from the hand-written `flagd/main.go` (`flagd/build.Dockerfile`; `test/integration` builds that Dockerfile). The Builder's binary is used only by `make build-flagd-full`'s CLI and log pins (finding 1).

What the release does today (`.github/workflows/release-please.yaml`, gated to `open-feature/flagd`, disabled here; verified by the opposer):
- **Images:** `flagd/build.Dockerfile` builds `flagd/main.go` into `/flagd-build` on `distroless/static:nonroot`, user 65532, for `linux/amd64` and `linux/arm64`, with an SBOM and cosign signatures. Tags: `ghcr.io/open-feature/flagd:<v>`, `:latest`, `:<v>-fips`, `:latest-fips`.
- **Archives:** `flagd_<ver>_<OS>_<arch>` and `flagd-fips_…`, each holding the binary, `LICENSE`, `CHANGELOG.md`, `README.md`, and an `sbom.xml` produced by `cyclonedx-gomod app` in `flagd/`.
- The matrix also builds `flagd-proxy`.

"R" means `github.com/open-feature-forking/openfeature-relay`.

## 0a. Drop-in: what an upgrading Operator sees

| Surface | How it stays identical | Proven by |
|---|---|---|
| Start command, flags, config keys, env vars, precedence | `runtime/cmd` unchanged | UC-001's pins against the built binary; the differential (PR 3) |
| Ports, endpoints, payloads, headers | Unchanged components | Differential: ConnectRPC v1/v2/legacy, OFREP single/bulk/304/SSE, flag sync, management paths |
| Readiness, startup and exit | Unchanged, except #78's items | Differential scenarios; startup time (Q6) |
| Metrics and spans | Unchanged names, attributes, buckets | `/metrics` diff; OTLP span diff (Q9) |
| `flagd version` | Byte-identical per build path (UC-001 Q10; Q3) | Differential `version`; 2b's per-path check |
| Image name, tags, entrypoint, user, base, platforms | `flagd/build.Dockerfile` unchanged (Q2) | `release-dry-run` with the literal upstream names (Q7) |
| Archive names and contents | Release steps unchanged (Q2) | `release-dry-run` |
| Binary build info `path` and the SBOM's main component | The `flagd` module path is kept (Q2) | `go version -m` and the SBOM in `release-dry-run` |
| Shutdown | #78's items only | Differential SIGTERM scenario |

**Not identical, and already so before UC-009:** `go install github.com/open-feature/flagd/flagd@<v>` fails, because `flagd/go.mod` carries local `replace` directives (17 on #96's branch; since UC-014). It is listed for the project lead as Q11, not as "stays identical".

## 0. Questions for the project lead

The recommendation comes first. Wherever something visible could change, it keeps today's behaviour.

- **Q1, the differential's baseline.** The branch carries upstream up to b23f82e, newer than the last release `flagd/v0.18.2`. Upstream commits since then (for example `50d0f559`, which changes debug logging) differ from v0.18.2 without being this repository's doing (finding 5).
  - **Recommendation:**
    - **Behaviour:** compare against flagd built from the upstream merge-base (b23f82e today), using upstream's own `flagd/build.Dockerfile` from a `git archive` of that commit. The commit is in this repository's history, so nothing is fetched.
    - **Image and release metadata:** compare against the published `ghcr.io/open-feature/flagd:v0.18.2` image, pinned by digest and pulled read-only.
    - When `upstream/main` is merged in, the merge-base moves with it, in the same merge PR.
  - *Alternative:* v0.18.2 for both, with a second `accepted.yaml` entry kind "upstream since v0.18.2, `<commit>`" that each pin move prunes.

- **Q2, which module the release builds (UC-001's gap).**
  - **Recommendation: keep today's release module.** The `flagd` module becomes the committed Builder output: the manifest gets `dist.module: github.com/open-feature/flagd/flagd` and `output_path: ../../flagd`.
    - The Builder writes `flagd/main.go` and `flagd/components/components.go`. With Q12 it also writes `flagd/go.mod`.
    - It writes its probe into a temporary directory, never into `flagd/`.
    - `flagd/components/inventory.go` and `inventory_test.go` go, because the generated `components.go` declares `Inventory()`.
    - `profiler.go`, the Dockerfiles and the tests stay.
    - CI regenerates into a temporary copy and fails on any diff (`check-flagd-full-generated`). That replaces `TestGeneratedComponentsEqualHandWritten`.
    - Today's binary build-info `path`, the SBOM's main component, both Dockerfiles and every release step stay as they are.
  - *Alternative:* release `distributions/flagd-full/build`, with module `R/distributions/flagd-full`. The cleaner Builder story, but the build-info path and the SBOM's main component change visibly.

- **Q3, version stamping.** Three build paths stamp today, in three formats (finding 6):

  | Path | Version | Commit | Date |
  |---|---|---|---|
  | Release | release-please's version | full `github.sha` | release-please's date |
  | `make build-flagd` | `dev` | short | `date +%FT%TZ` (local time, literal `Z`) |
  | Builder default | `dist.version` (`0.0.0`) | short | RFC 3339 UTC |

  - **Recommendation:** `relay-builder` gains `--dist-version`, `--commit` and `--date` as opt-in overrides, plus `--output` so CI can regenerate into a temporary copy. Each path passes exactly today's strings, so `flagd version` is byte-identical per path.
  - *Alternative:* the release job rewrites `dist.version` in a manifest copy, and the other paths keep the Builder's formats. That changes `make build`'s output (visible to developers, not to Operators).

- **Q4, UC-009 step 8 against UC-001 Q10.** Step 8 has `flagd version` name flagd-full; UC-001 Q10 keeps `flagd version` byte-identical, with the identity behind `--verbose`.
  - **Recommendation:** keep today's output, and amend step 8 and FR-034 to `flagd version --verbose`.
  - *Alternative:* the identity in the default output. That is visible, so not recommended.

- **Q5, which differences the differential allows, and A4.**
  - **Recommendation:**
    - `test/upgrade/accepted.yaml` holds two entry kinds. A `#78` entry names its #78 item. A `known-break` entry names the use case that removes it; today that is only `go install` (Q11, UC-012).
    - Every other difference fails the run. A #78 item without an entry, or an entry without an item, also fails.
    - UC-009 A4 is amended to "with the retry and readiness behaviour the migration notes describe", because #78's first item (a failed first fetch no longer exits flagd) contradicts its wording.
  - *Alternative:* restore today's exit on a failed first fetch behind an opt-in setting. Closer to drop-in, but it reopens a decision the project lead already made.

- **Q6, startup time (NFR-002, BR-005).**
  - **Recommendation:** in the `upgrade-test` job, 10 interleaved runs of baseline and candidate on the same runner, each timed from container start to the first `200` on `/readyz`. Gate on the medians within 10%, with one re-measure before failing, and put the numbers in the job summary.
  - *Alternative:* report only, with no gate.

- **Q7, proving the release without publishing (BR-007).**
  - **Recommendation:** a `release-dry-run` job, gated like `docker-local` (`FULL_CI` or a manual run). It runs the release's build steps from one script that the release workflow also calls; the script keeps the `flagd-proxy` path. It pushes nothing and signs nothing, and checks:
    - archive names and contents;
    - `flagd version`;
    - `go version -m` (path, and the FIPS tags);
    - the image's entrypoint, user and base digest;
    - the tag list, which it asserts as the literal upstream names (`ghcr.io/open-feature/flagd:<v>` and so on), not as names derived from `github.repository_owner`. Derived names would render `open-feature-forking` here (finding 7).
  - *Alternative:* leave the release workflow untouched until UC-012. UC-001's gap then stays unproven.

- **Q8, the migration notes.**
  - **Recommendation:** `docs/guides/upgrade-to-flagd-full.md`:
    - what stays the same (section 0a);
    - #78's 14 items, each with what the Operator sees and what to do;
    - known breaks (Q11);
    - rollback (A5);
    - a short embedder section from #89 that points to UC-015.

    It is checked against `accepted.yaml`.
  - *Alternative:* one guide only, in UC-015.

- **Q9, spans at binary level (BR-006, FR-033).**
  - **Recommendation:** both runs export OTLP over gRPC to a receiver in the test. The test compares names, kinds, scopes, attributes, status and parent links, without IDs or timing.
  - *Alternative:* rely on the in-process span pins.

- **Q10, sources in the differential (BR-003).**
  - **Recommendation:**
    - **Run in the differential:** `file:` (both watchers), `http://`, `https://`, `grpc://` (a flag sync endpoint as source) and `envoy://`.
    - **Startup scenario only:** `gs://`, `azblob://`, `s3://` and `core.openfeature.dev/`, against unreachable endpoints, comparing the first error line and readiness. UC-003's stub tests cover their delivery.
    - **Emulators:** only under `FULL_CI`.
  - *Alternative:* emulators always on.

- **Q11 (new), `go install …@<v>` (finding 4).** It already fails before UC-009, because `flagd/go.mod` has local replaces. Restoring it needs published component modules without replaces, which is UC-012.
  - **Recommendation:** a `known-break` owned by UC-012, listed in the migration notes. The binary archives and images are the supported install paths, as they are in flagd's installation docs.
  - *Alternative:* UC-009 waits for UC-012's module tags, so `go install` works at the first flagd-full release.

- **Q12 (new), `flagd/go.mod` generated or hand-kept (finding 2).** The Builder generates `go.mod` (with a `DO NOT EDIT` header, the manifest's requires and replaces) and runs `go mod tidy`.
  - **Recommendation:** generated. The manifest becomes the one source of the module's requires and replaces, as in the OpenTelemetry Collector Builder. Renovate and dependency bumps then edit the manifest, and `check-flagd-full-generated` catches a hand edit. Tidy reads `flagd/`'s own tests, so their test dependencies stay in the file.
  - *Alternative:* hand-kept. The Builder gets a mode that leaves `go.mod` and skips tidy, plus a check that `flagd/go.mod`'s requires and replaces equal the manifest's.

- **Q13 (new), `components.Official()` or `components.Components()` (finding 3).** The generated package exports `Components()`. Hand-written `flagd/components` exports `Official()`. Three callers use `Official()`: `runtime/accept_test.go`, `runtime/components_test.go` and `runtime/cmd/start_config_characterization_test.go` (a UC-001 pin; only its setup line changes).
  - **Recommendation:** callers switch to `Components()`, and #89's entry for `runtime.Official` is updated. No release has carried `flagd/components.Official()`, so nobody outside depends on it.
  - *Alternative:* the template also emits `Official()` as an alias for every distribution.

## 5. Risks

- **Notes drifting from reality.** `accepted.yaml` ties every allowed difference to a #78 item or a named known break, and the guide is checked against the same list.
- **Flaky differential.** Normalization is explicit and commented. Startup timing gets one re-measure.
- **Generated code in `flagd/`.** 1b refuses files without the generated header and keeps the probe out. 2a removes `inventory.go` and its duplicate `Inventory()`.
- **Module cycle.** The runtime's tests import the `flagd` module. Go allows the cycle; `go mod tidy` must stay clean in `flagd/` and `runtime/`.
- **Upstream merges** move the behaviour baseline (Q1) in the same merge PR, so upstream's own changes never appear as differences.
- **External pull.** The v0.18.2 image is pulled read-only, pinned by digest. Nothing is pushed.
- **CI time.** `upgrade-test` builds two images (candidate and merge-base) and pulls one, about 8 minutes. The emulators stay behind `FULL_CI`.
- **C-004.** `Official()` → `Components()` and the removed `Inventory` file go into #89 (Q13).
