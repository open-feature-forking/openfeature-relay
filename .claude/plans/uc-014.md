## 0. Spec questions (the plan assumes the recommendation)

- **Q1, how to split the modules.**
  - **Recommendation:** carve out with **unchanged import paths**. `core` becomes the light core module (NFR-006), and the heavy packages and the two embeddable components each get a nested `go.mod` in their current directory.
  - *Why:* providers then change only `go.mod`, never an import, and the opposer's scratch carve shows the module graphs come out clean.
  - **Cost to note in issue #26:** eleven new tag series of the form `<dir>/vX.Y.Z` (for example `core/pkg/evaluator/v0.1.0`) once releases start, owned by UC-012.
  - Alternative: new top-level module paths, which rewrites imports in flagd, flagd-proxy and every provider.
- **Q2, OTel through the sync providers.**
  - **Recommendation:** accept that the file and gRPC sync modules carry the OTel metric API (via `syncmetrics`) for UC-014.
  - *Why:* NFR-005 binds only the evaluator and flagd's configuration format, and the sync metrics move behind the telemetry provider factory in UC-003/UC-006.
- **Q3, FR-044 and A5 (a flag sync request names its configuration format).**
  - **Recommendation:** gap owned by UC-017.
  - *Why:* it needs the flag sync endpoint to select documents by format without a protobuf change (C-005), and flagd's format is already the default every request gets.
- **Q4, typed adapter (steps 7–8, BR-008, the adapter half of A6).**
  - **Recommendation:** gap owned by UC-007.
  - *Why:* the adapter and the untyped evaluator arrive together there; providers keep today's typed `Resolve*Value` until then.
- **Q5, acceptance without touching go-sdk-contrib.**
  - **Recommendation:** two parts.
    - The published Go provider v0.8.0 in `test/integration` compiles against this repository's modules through `replace`, so the in-process suite runs on our evaluator.
    - Two minimal in-repo example modules (file-only, and file plus gRPC) prove the module-graph postconditions.
  - *Why:* containment keeps go-sdk-contrib read-only, and a module graph can only be checked per module, so the two embeddings need separate modules.
- **Q6, flows without a test.**
  - **Recommendation:** A2 (vendor engine) is a gap owned by UC-007/UC-019; A7 (no hooks) and A8 (process only) get no test.
  - *Why:* A7 and A8 have no system behaviour, and the engine module needs UC-007's evaluator factory.
- **Q7, unpublished modules.**
  - **Recommendation:** each consumer requires every module in its *transitive* build list at `v0.0.0-00010101000000-000000000000`, with a `replace` to the local directory, **including `core` itself**. Consumers are `flagd`, `flagd-proxy`, `test/*`, the examples and each nested module.
  - *Why:* replaces in a dependency's `go.mod` don't apply to the main module, and today `flagd` already fails `GOWORK=off` because it requires published core v0.19.0, which lacks `configformat`.
  - Released versions can't be tested in the incubator, because the module path still points the Go proxy at upstream. UC-012 inherits the release rule in section 6.
- **Q8, the evaluator's compat `SetState` and `store.NewFlags`.**
  - **Recommendation:** keep both.
  - *Why:* the published provider calls them; the evaluator module then requires flagd's format module, which is the allowed direction, and UC-015 retires them.
- **Q9, the shared poller in core (new, from finding 8).**
  - **Recommendation:** `sync/internal/polling`, and with it `robfig/cron/v3`, stays in core for UC-014.
  - *Why:* it serves the HTTP and blob sync providers and is exactly what UC-003's shared poller (FR-045) redesigns. Moving it now would be done twice.
  - NFR-006 ("modules its data types need") is therefore met except for cron, as a named gap owned by UC-003.

## 3. Design in brief

Nested modules use their directory's import path, e.g. `module github.com/open-feature/flagd/core/pkg/evaluator`.

| Module (directory under `core/pkg/`) | Direct requirements | Notes |
|---|---|---|
| `core` (root) | uuid, go-memdb, `robfig/cron/v3`, testify, zap, protobuf, `gopkg.in/yaml.v3` (SHA-3 is stdlib) | Light core: `model`, `logger`, `store`, `sync` (types), `configformat`, `formattest`, `utils`, `fips`, `certreloader`, `notifications`, `sync/internal/*` (Q9), `sync/testing`, `internal/*` |
| `evaluator` (+ `mock`) | `core`, `configformat/flagd`, jsonlogic, murmur3, cbor, x/mod | Embeddable |
| `configformat/flagd` | `core`, jsonschema, flagd-schemas | Embeddable; no evaluator, no jsonlogic |
| `sync/syncmetrics` | OTel metric API | Q2 |
| `sync/file` | `core`, `syncmetrics`, fsnotify | |
| `sync/grpc` (+ `credentials`, `nameresolvers`, `mock`) | `core`, `syncmetrics`, gRPC, buf-generated sync | |
| `sync/http` | `core`, `syncmetrics` | |
| `sync/blob` | `core`, `syncmetrics`, gocloud | |
| `sync/kubernetes` | `core`, `syncmetrics`, k8s | |
| `sync/builder` (+ `mock`) | Every sync module | |
| `telemetry` | `core`, OTel, gRPC, connect | |
| `service` (+ `ofrep`) | `core`, `evaluator`, connect | |

- **Replace rule (Q7):** every `go.mod` (consumers and nested modules) requires and replaces `core` and every carved module in its transitive build list. In the scratch carve, `flagd` needed all eleven. `go mod tidy` with `GOWORK=off` in each module directory is what proves the set is complete.
- **Dockerfiles:** the download step binds the whole `./core` directory (`--mount=type=bind,source=./core,target=./core`) instead of `core/go.mod`/`go.sum`, in all three Dockerfiles.
  - Cost: the module download layer is invalidated by any `core` change, not only `go.mod` changes.
  - Alternative: one bind per nested `go.mod`/`go.sum`, 22 lines per Dockerfile that every new module must extend.
- **Examples:** two modules, because module graphs belong to modules (finding 4).
  - `test/inprocess-example/file`: `go-sdk`, `core`, `evaluator`, `configformat/flagd`, `sync/file`. A minimal provider over store, format and evaluator, fed by file sync, resolving through today's typed methods.
  - `test/inprocess-example/filegrpc`: the same plus `sync/grpc`.

  Both carry the full replace set, and both run in `make test` through `test-inprocess-example`.

## 6. Risks

- **Silent gates.** Directory patterns stop at nested modules. Every pattern-based target moves to `CORE_MODULE_DIRS` in PR 1, before any carve, and `check-core-coverage` fails if a package drops out. The benchmark gate checks that the evaluator is actually in `benchmark.txt`.
- **Incomplete replaces.** A missing `replace` makes Go fetch `v0.0.0-…` from the proxy and fail. Per-module `GOWORK=off go mod tidy` and builds catch it; CI's workspace builds would not.
- **Docker cache.** Binding all of `./core` in the download step makes the module layer rebuild on any `core` change. That's acceptable for the PoC; UC-002 (images) can switch to per-file binds.
- **Release rule for UC-012** (finding 6):
  - Each carved module must require the first core release that no longer contains its packages, and core is released first or together with them; otherwise consumers hit "ambiguous import".
  - The module paths point the Go proxy at upstream `open-feature/flagd`, so nothing here is `go get`-able. The precondition "released versions a provider can pin" is untestable in the incubator.
- **C-003.** No code changes, only `go.mod` boundaries, Makefile targets and Dockerfile mounts. The integration suites, FIPS tests and pinned tests prove behaviour; the image name and CLI are untouched.
- **NFR-001.** Evaluation code is unchanged; the benchmark gate checks that the evaluator benchmarks still run.
- **Over-building.**
  - No release tooling (UC-012), typed adapter or router (UC-007), flag sync format selection (UC-017), poller move (UC-003) or flagd module split (UC-001).
  - The examples are test fixtures, not providers.
- **Containment.** go-sdk-contrib stays read-only; the published v0.8.0 is consumed from the module proxy, as `test/integration` already does.
