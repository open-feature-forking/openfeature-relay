## 1. Seams step 6 builds on

Each seam is created once, by the UC-004 step named, and changed by step 6 only where stated. UC-004 defines the seam and leaves the behaviour step 6 needs to step 6.

**S1, events and the event bus** (`R/core/pkg/events`, step 2a; the schema is Q2, the overflow rule Q3).
- Kinds `configuration_change`, `evaluation`, `tracking`, and one type each:
  - `ConfigurationChange{Time; Source, Format, FlagSet, Version string; Added, Updated, Removed []string; Missed int}`.
  - `Evaluation{Time; FlagKey, FlagSet, Format, Endpoint, Variant, Reason, ErrorCode, TargetingKey string; Value any; HasValue bool; Origin}`. `Endpoint` is the type of the endpoint's factory; an absent value is `HasValue=false`, never the caller's default.
  - `Tracking{Time; EventName, TargetingKey string; Value float64; Details map[string]any; Origin}`.
  - `Origin` is `service` or `in-process` (Q2).
- `Bus`: `Subscribe(SubscribeOptions{Kinds; Buffer int; OnDrop func(Kind)}) *Subscription`, `Publish(Event)`, `HasSubscribers(Kind) bool` (one atomic load), `Close()`. A subscription's channel is its only buffer. `OnDrop` is called once per dropped event.
- **Who publishes:**
  - Configuration change events: only the runtime, after a format accepts a delivery (step 3b). One event per document with at least one added, updated or removed key, or a new document version.
  - Evaluation events: the resolver the runtime injects, through an observer on the typed adapter (Q4, steps 2b, 3c). The official endpoints publish nothing by hand. An endpoint that uses a format's evaluator directly (A2) calls `events.PublishEvaluation`.
  - Tracking and relayed evaluation events: the endpoint that collects them, through `events.PublishTracking` and `PublishEvaluation` with origin `in-process`.
- **Step 6:** E2 has no `core/pkg/events` commit and no E3a. E3b becomes a check that each official endpoint publishes once per resolved flag. An event sink subscribes with `Buffer` set to its `bufferSize` and `OnDrop` counting through the telemetry provider (`reason=buffer_full`); its pipeline reads the subscription's channel, with no second queue. A configuration change event with `Missed > 0` reaches the sink like any other event; the sink rereads nothing.

**S2, the middleware seam** (`R/core/pkg/middleware`, step 2c).
- UC-004 creates the package with the selector functions only:
  - `BindSelector(ctx, expression) context.Context` and `BoundSelector(ctx) (store.Selector, bool)`. This is the one key for a bound selector.
  - `EffectiveSelector(ctx, clientExpression) (store.Selector, error)`, with the semantics of Q6.
  - `WithAttributes` delegating to `evaluator.WithAttributes` (one attribute key, UC-007's).
- Every endpoint writes the effective selector into `store.SelectorContextKey{}`, so the router keeps reading one key.
- `service.Settings.HTTPMiddleware func(http.Handler) http.Handler` is the chain an HTTP endpoint applies. Without middleware it is the identity.
- **Chain position:** `h2c → CORS → HTTPMiddleware → instrumentation (HTTP metrics, spans) → handler`. OFREP has no h2c, and its per-route metrics sit inside its router, so there it is `CORS → HTTPMiddleware → router`. The chain therefore sees every plaintext gRPC call after h2c.
- **Ordering rule, before and after M3:** CORS, when present, handles a request before any other middleware, so no other middleware answers a CORS preflight. Until M3 this holds because CORS is endpoint-internal, outside `HTTPMiddleware`. Once M3 makes CORS a chain member, startup fails, naming the order, when a `cors` middleware is configured anywhere but first in `Components.Middleware`. The runtime never reorders silently (UC-005 BR-003). Step 6 pins it with `TestPreflightBeforeAuthentication`.
- **Step 6:** M2 adds `Middleware`, `Factory`, `Chain` and `middlewaretest` to the same package. M3 fills `HTTPMiddleware` with `Chain(...)`, makes CORS the chain's first member and enforces the ordering rule (the position is then unchanged), and switches the official endpoints to `EffectiveSelector`.

**S6, shutdown order and time limit** (`runtime.start`, step 3f; the budget is Q11).
1. `ctx` ends. Sync providers and endpoints stop in the runtime's errgroup. Each endpoint returns within the endpoint budget, a contract case.
2. `Bus.Close()`: later publishes are dropped, and subscriptions' channels close once drained.
3. Shutdown hooks run in the order they were registered (`r.onShutdown(name, func(ctx) error)`), each with a context carrying the remaining hook budget. Errors are logged.
4. `start` returns after the last hook.
- **Step 6** registers the event sinks' flush, then the telemetry provider's `Shutdown`, in that order. UC-004 pins the order with fake hooks (`TestShutdownOrder`).

## 2. Spec questions

All decided by the project lead on 2026-11-03, each as recommended. The recommendation comes first; the alternative is kept for the record.

- **Q1, the service endpoint interface and declared needs (step 2, step 5, BR-004).** **Decided: as recommended.** PR 2. Today's `IFlagEvaluationService` has `Notify` and `Shutdown`, typed calls BR-002 rules out.
  - **Recommendation:** `Endpoint{Serve(ctx) error}`: `Serve` blocks, ends client connections and returns nil when `ctx` ends; an error stops the distribution (BR-010). `Factory{Type(); Needs() Needs; Create(Settings) (Endpoint, error)}` with `Needs{Router bool; Format string}`. `Resolver` is set only for `Needs.Router`, `Evaluator` only for `Needs.Format`. `ValidateDeclarations(Factory)`. `IFlagEvaluationService` and `IKubeSyncService` stay, deprecated.
  - *Alternative:* keep `Serve`/`Notify`/`Shutdown` with a generic `Notify`. That is a typed call path beside the bus.
- **Q2, the event schema and origin values (merged with step 6's Q11).** **Decided: as recommended.** PR 2. The glossary lists flag key, flag set, variant, value, reason, targeting key and origin.
  - **Recommendation:** S1's schema: the glossary fields plus the time, error code, configuration format, endpoint type and `HasValue`, plus `Missed` on configuration change events. Origin is `service` (resolved by a service endpoint of this distribution) or `in-process`.
  - *Alternative:* origin `remote`/`in-process`, the names OpenFeature providers use (an RPC provider is "remote"). The time, format and endpoint type could also be left out, leaving sinks to stamp the time. The schema decision itself is the same either way.
- **Q3, a subscriber that falls behind (BR-006, BR-008, UC-020 BR-003).** **Decided: as recommended.** PR 2.
  - **Recommendation:** publishing never blocks. A full subscription drops the event and calls `OnDrop`. For configuration change events, the next event delivered to that subscription carries `Missed`; an endpoint then rereads the store (BR-006), and an event sink just counts the drops (S1).
  - *Alternative:* no `Missed` marker. An endpoint that misses a change serves stale announcements until the next one.
- **Q4, who publishes evaluation events (UC-004 step 3, A2, FR-037, UC-021 BR-003).** **Decided: as recommended.** PR 2. The spec makes each endpoint publish. Done by hand, every endpoint has to get bulk requests right, and step 6's E3b and a core decorator together would publish twice.
  - **Recommendation:** the core publishes. The typed adapter gets `typed.WithObserver(func(ctx, evaluator.Request, evaluator.Result))`, called once per flag with the `Result` the adapter finally returns to the client: its own error code (`TYPE_MISMATCH` included), the converted value, and `HasValue=false` where it answers with the caller's default. `Event.Value` is that converted value. The router stamps `Result.Format` on every path, the single-evaluator fast path included. The runtime builds one typed adapter per endpoint, with `events.EvaluationObserver(bus, factory.Type())`; the observer returns immediately when nothing subscribes. Amend UC-004 step 3 and A2 step 2, and UC-021 BR-003: "resolves through the injected router, which publishes an evaluation event per resolved flag; an endpoint that uses a format's evaluator directly publishes them itself".
  - *Alternative:* the endpoints publish, as worded today (step 6's E3b), and the contract counts events per resolved flag.
- **Q5, NFR-013's benchmarks (merged from step 6's Q13).** **Decided: as recommended.** PR 2. NFR-013 names the evaluator benchmarks, but the evaluator publishes nothing (UC-020 BR-006), so they cannot show the cost.
  - **Recommendation:** amend NFR-013 to name the endpoint benchmarks of S7. With no subscriber, allocs/op stay equal to PR 1's baseline. The evaluator benchmarks remain NFR-001's gate.
  - *Alternative:* keep the wording; report the endpoint benchmarks without gating on them.
- **Q6, a bound selector meets the client's selector (UC-004 A6 against UC-005 BR-005, FR-047; merged with step 6's Q8).** **Decided: as recommended.** PR 2. UC-004 A6 says the bound selector comes "before a selector the client sent"; UC-005 BR-005 says the client "may narrow it further".
  - **Recommendation:** the intersection. A key set only by the bound selector is taken from it; a key set only by the client narrows; a key both set to different values matches no flags: `FLAG_NOT_FOUND` for a single flag, no flags for a bulk request, a flag sync or an event stream. Amend UC-004 A6 step 2 to say so.
  - *Alternative:* the bound selector wins, and a conflicting client key is ignored. A client asking for flag set B then silently gets A.
- **Q7, which official endpoints move from `store.Watch` to the bus.** **Decided: as recommended.** PR 4. `store.Watch` follows the flags table, which only flagd's format writes.
  - **Recommendation:** the OFREP event stream moves (FR-046 asks for every format). The flag evaluation event stream and flag sync keep `store.Watch`, which the glossary allows (C-003: their notifications stay as pinned). Named gaps: vendor flag changes on the flag evaluation event stream (UC-019), flag sync of vendor documents (UC-017).
  - *Alternative:* move all three. The flag evaluation event stream would then announce changes to keys a higher-priority source shadows, which it does not today.
- **Q8, OFREP validators against BR-007.** **Decided: as recommended.** PR 4. Today the bulk ETag hashes the response (etag.go:14), and the event stream's `flagConfigEtag` fingerprints the flags (sse/tracker.go:203).
  - **Recommendation:** `flagConfigEtag` and refetch events come from the document versions behind the selector (a hash of the sorted (format, source, flag set, version) tuples). The bulk ETag stays a hash of the response: it must cover the evaluation context, and `$flagd.timestamp` targeting changes results without a version change. Amend BR-007: "change announcements and configuration validators come from document versions; a response validator may hash the response it validates".
  - *Alternative:* bulk ETag = hash(document versions, evaluation context). It answers 304 without evaluating, but answers wrongly for time-dependent targeting.
- **Q9, probes without the flag evaluation endpoint (FR-017).** **Decided: as recommended.** PR 3.
  - **Recommendation:** the runtime serves the management port (S5).
  - *Alternative:* it stays in the flag evaluation endpoint, and "probes without it" is a gap for UC-001.
- **Q10, flag sync's `Emit(source)`.** **Decided: as recommended.** PR 3. It gates serving until every source delivered once (or 5 s), and stamps `Last-Modified` on every delivery, changed or not (sync_service.go:180).
  - **Recommendation:** the runtime closes `Settings.Initialized` once every source has been accepted, and the 5 s timeout stays. `Last-Modified` is stamped on configuration change events. Behaviour change: an unchanged redelivery no longer moves it (its own commit).
  - *Alternative:* a fourth event kind, "delivery accepted". BR-002 names three.
- **Q11, the shutdown time limit (S6; UC-004 BR-010, UC-020 BR-005).** **Decided: as recommended.** PR 3. Today each endpoint shuts down within 5 s, in parallel, and nothing runs after them.
  - **Recommendation:** two budgets of 5 s each: the endpoint stage (today's), then the hook stage, shared in order by event sink flushes and the telemetry provider's shutdown. Shutdown takes at most 10 s, well inside Kubernetes' default 30 s grace period.
  - *Alternative:* one 5 s budget for the whole shutdown. A client stream that holds an endpoint's graceful shutdown open then leaves no time to flush sinks or telemetry.
- **Q12, staleness (FR-052), inherited from UC-003 (its Q8).** **Decided: as recommended.** PR 7. UC-003 BR-005 counts from "the last accepted delivery", but a fetcher delivers only when the version changes, so an unchanged healthy source would go stale.
  - **Recommendation:** count from the last successful contact: a successful fetch, changed or not, or an open stream. An optional `LastContact() time.Time` on a streaming sync provider, implemented by the fetching sync provider and by `flagd-grpc`. A source setting `staleAfter`. Amend UC-003 BR-005 and BR-008.
  - *Alternative:* move FR-052 to UC-010.
- **Q13, the webhook fetch trigger, inherited from UC-003.** **Decided: as recommended.** PR 6's status commit. It is not a service endpoint: the bus has no "fetch now" event, and a trigger runs per source.
  - **Recommendation:** move the gap to UC-019, with the server-sent event and vendor change triggers.
  - *Alternative:* an official `webhook` fetch trigger in `sync/http` here.
- **Q14, examples, alternative flows and the collector (NFR-010, A3, FR-039).** **Decided: as recommended.** PR 5.
  - **Recommendation:**
    - `test/service-example` (requires `R/core` only) holds one endpoint over plain HTTP and JSON. `GET /v0/flags/{key}` and `GET /v0/flags` resolve through the router. `GET /v0/changes` long-polls for a configuration change event that concerns the selector and carries a validator from document versions. It covers the main scenario, A4 and A6.
    - A1, A3, A5 and A7 are covered by `servicetest`'s stubs. A2 is covered by a test endpoint in `test/configformat-example`. The official flag sync endpoint is the real A1 case.
    - There is no official collector endpoint: the contract checks origin `in-process` on a stub. The official collector is UC-021's (its A1), and FR-039 becomes `In Progress`.
  - *Alternative:* one example module per flow, plus an official collector endpoint here.

## 7. Risks

- **C-003, behaviour changes,** each in its own commit and listed in the PR text and UC-009's migration notes:
  - Flag sync's `Last-Modified` moves only on a change (Q10).
  - The OFREP event stream's `flagConfigEtag` values change (opaque, same meaning), and vendor-format changes now send refetch events (Q8).
  - Shutdown may take up to 10 s once step 6 registers hooks (Q11); with UC-004 alone nothing runs after the endpoints.
  - Unchanged: CLI flags, ports, management paths and status codes, readiness, spans, metric names, payloads, the notifications on the flag evaluation event stream and on flag sync.
- **C-003, two delivery paths.** flagd-full goes through `Accept` (1e pins the texts); a `Runtime` literal keeps `SetState`. The literal path exists for UC-018's pins and embedders; UC-015 decides whether it retires.
- **Concurrency.** Publishing under `r.mu` never blocks (2a); `TestPublishNeverBlocks` and the contract's `Missed` case cover it.
- **NFR-001, NFR-013.** The observer is nil-checked in the typed adapter, and returns before building an event when nothing subscribes; `Result.Format` is one assignment. `TestAdapterAllocs`, `TestObserverNoSubscriberAllocs` and the endpoint benchmarks gate it. If allocs rise, the step stops and reports with numbers.
- **NFR-005, NFR-006.** The new core packages use the standard library, `store`, `evaluator` and `logger`; the rows in 2e pin it. `typed` and `router` gain no import.
- **BR-001.** `test/service-example`'s row forbids every flagd module but core.
- **Cross-plan drift.** Section 1 is the single definition; a step-6 change to a seam is a change to this plan first.
- **C-005.** No protobuf change. **C-006:** PRs 2–4 are shaped for upstream; PR 6's spec changes are incubator-only.
- **Over-building.** No middleware factory or chain (UC-005), telemetry factory (UC-006), event sinks (UC-020), collector endpoint (UC-021), flag sync format selection (UC-017), builder (UC-001) or webhook trigger (Q13).
