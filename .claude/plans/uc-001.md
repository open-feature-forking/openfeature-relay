## 0a. Drop-in: what flagd-full keeps

The project lead's goal is to make it easier for everyone to build a relay, without anyone noticing a difference in flagd-full. Each surface, with the pin or rule that holds it:

| Surface | How flagd-full stays identical |
|---|---|
| Binary name | The Builder names the binary `flagd` (`dist.binary`, default `flagd`); the flagd-full manifest pins it and 7a checks `<output>/flagd` (D2) |
| CLI flags, config keys, environment variables | Pin 1b; Q15's table keeps every flag in `runtime/cmd` with its name and default |
| Help text, startup failures, exit codes | New pin 1f (D3) |
| `flagd version` | Byte-identical (Q10, D1): same first line (release version, short commit, date), no new line; the distribution identity is opt-in |
| Version stamping | `main.version`, `main.commit`, `main.date` stay the `-X` targets in flagd's `main` and in every generated `main`, so the Makefile and all three Dockerfiles keep their stamping (N5) |
| Build flags | The Builder's defaults match today's release build: `CGO_ENABLED=0`, no `-trimpath` (stack traces keep today's paths). Anything else is opt-in through `GOFLAGS` (Q13) |
| Image | `ghcr.io/open-feature/flagd`, built by the unchanged Dockerfiles from the `flagd` module, with the same `/flagd-build` entrypoint; `profiler.go` stays there |
| Ports, endpoints, payloads, headers, readiness, metrics, spans, shutdown | UC-004's and step 6's pins, plus 1d (official components) and 1e (effective endpoint settings), unchanged through the split |
| Startup | flagd's format stays the default format (Q6 changes nothing for flagd-full); settings at their defaults never touch absent components (N3) |
| Module graph | Pin 1c: only documented path moves |

A visible change would be a question with "keep today's behaviour" as the recommendation. Revision 3 has none left for flagd-full. Q10's alternative is the only visible option, and it is not recommended.

## 0. Spec questions

The recommendation comes first.

- **Q1, the Builder's name and module.** **Decided: as recommended.** The glossary rules out "ocb", "generator" and "flagd-builder".
  - **Recommendation:** a CLI `relay-builder` in a new module `R/builder` (`builder/cmd/relay-builder`). It depends on no relay module. It calls the `go` binary on `PATH` (or `--go`), always with `GOWORK=off`.
  - *Alternative:* a `flagd build` subcommand. Every distribution would then carry the builder.
- **Q2, the manifest schema (FR-001, FR-002, BR-001, BR-003, BR-007).** **Decided: as recommended.**
  - **Recommendation:** YAML, read with `yaml.v3` nodes so every error names its line and column (A1):

    ```yaml
    dist:
      name: flagd-custom                # mandatory
      version: 1.2.0                    # mandatory, semantic version
      output_path: ./build/custom       # mandatory
      module: example.com/flagd-custom  # generated module path; default derived from name
      binary: flagd                     # binary name; default flagd (D2)
    runtime: {module: R/runtime, version: v0.14.0}   # optional, Q9
    sync_providers:        [{module: R/sync/file, version: v0.14.0}]
    configuration_formats: [{module: R/configformat/flagd, version: v0.14.0}]
    evaluators:            [{module: R/evaluator/flagd, version: v0.14.0}]
    engines:               []           # Q4
    service_endpoints:     [{module: R/service/ofrep, version: v0.14.0}]
    telemetry:             {module: R/telemetry/otel, version: v0.14.0}   # at most one; noop if absent
    middleware:            []
    event_sinks:           []
    replaces:                           # Q14: one line per relay module in repository manifests
      - {module: R/core, path: ../../core}
      - {module: R/runtime, path: ../../runtime}
      - {module: R/sync/file, path: ../../sync/file}
      # … every other relay module in the build list
    ```

    An entry may carry `import:`, the package that holds the factory (default: the module root). Validation covers BR-001 to BR-004, BR-007 and BR-002's cardinalities. A version must be an exact semantic version or pseudo-version.
  - *Alternative:* the OpenTelemetry Collector Builder's `gomod: "path vX"` strings.
  - **Decision (project lead): a distribution may bring its own command line.** The manifest takes an optional `cmd: {module, version, import?}`; the generated `main` calls that package's `Execute(info, components, inventory)`, the signature of `runtime/cmd`, which is the default, so flagd-full's generated `main` is unchanged. At most one entry; a module without a matching `Execute` fails the compile and the error names it. The motivation is a drop-in Flagsmith Edge Proxy (#94), whose operators use their own flags and configuration keys.
- **Q3, how generated code finds a factory.** **Decided: as recommended.**
  - **Recommendation:** each component package exports `NewFactory()`, returning its group's core interface. A sync provider module exports `NewFactories() []sync.Factory`, because a fetcher ships its own fetch triggers. A missing function fails compilation, and the error names the component (A12). Neither function takes arguments: telemetry reaches sync providers and endpoints through `Settings.Telemetry` (step 6 T4d), which is a precondition of PR 5.
  - *Alternative:* `Register(*distribution.Components)` per module.
- **Q4, engine modules against BR-004.** **Decided: as recommended.**
  - **Recommendation:** an `engines:` group. The module is listed once and exports `NewConfigurationFormatFactory()` and `NewEvaluatorFactory()`. Amend UC-001 step 2 and BR-002.
  - *Alternative:* list the module under both groups, and amend BR-004.
- **Q5, checking needs and schemes before compiling (step 8, BR-014, BR-015, A9–A11).** **Decided: as recommended.**
  - **Recommendation:** a generated `probe/main.go` imports only the core module and the component packages, and prints every factory's group, type, schemes and needs as JSON. The Builder runs it with `go run ./probe` after resolution and checks endpoint needs, evaluator formats and scheme clashes, and warns on an unused evaluator.
    - The probe runs for the **host**: `GOOS`, `GOARCH` and `GOFIPS140` are unset for that one call, so a cross-build still runs it.
    - It uses the final build's other flags (`CGO_ENABLED=0`, plus any `GOFLAGS`), so most packages share the build cache with the final compile.
    - The runtime keeps its own startup checks.
  - *Alternative:* a static `relay-component.yaml` in every component module, which can drift from the code.
- **Q6, flagd's configuration format and evaluator are selectable, not built in.** **Decided: as recommended.**
  - **Recommendation:** the runtime takes both from `Components`, like any format or evaluator.
    - It creates the default format through the factory whose type is `configformat.DefaultType`, when that factory is selected. A source without a format in a distribution without flagd's format fails startup, naming the available formats.
    - The router is built generically from `Components.Evaluators`. flagd's `strictNumericRange` (TODO #2101) reaches the JsonLogic evaluator through its factory's `Config`, and reaches the typed adapter through the runtime's plain `Config.StrictNumericRange`.
    - `pkg/evaluation`'s flagd-specific parts (`NewEvaluator` over `flagdeval.JSON`) move into `evaluator/flagd`, where UC-007's endpoint pins keep using them from test code.
    - The `SetState` fallback stays only as `Runtime.Evaluator evaluator.IEvaluator`, a core interface that a `Runtime` literal sets (UC-018's pins). The runtime imports no evaluator module for it.
  - *Alternative:* keep them built in, and amend NFR-011 and BR-005.
- **Q7, the module split (phase 4; NFR-004, NFR-006, C-004).** **Decided: as recommended.**
  - **Recommendation:** new modules:
    - `R/runtime`: `pkg/runtime`, and the start and version commands as a library (`runtime/cmd`).
    - `R/service/flag-evaluation`, `R/service/ofrep` and `R/service/flag-sync`.
    - `R/service/transport`: shared h2c, CORS, compression and codec helpers; not a component.

    The `flagd` module keeps its path as flagd-full's main module, with `main.go` and a hand-written `components.go`, until UC-009 regenerates it. The removed `flagd/pkg/...` paths go to UC-015.
  - *Alternative:* one `R/service` module for all endpoints.
- **Q8, where `Components` lives.** **Decided: as recommended.**
  - **Recommendation:** `R/core/pkg/distribution` holds `Components` (moved; `runtime.Components` stays as an alias), `Info` and `Inventory`. All of them are plain data over core types.
    - The generated `components/components.go` is an importable package, not `package main`, so tests can import it (N4). It imports only core and the components.
    - The generated `main.go` declares `version`, `commit` and `date` as today's `main` does, imports `<module>/components`, and calls `runtimecmd.Execute(info, components.Components(), components.Inventory())`.
    - flagd's hand-written package has the same shape: `github.com/open-feature/flagd/flagd/components`.
    - `Inventory` lists group, type and module. Versions are filled at run time from `debug.ReadBuildInfo()`, so a replaced module shows what was actually linked (UC-011 step 5).
  - *Alternative:* keep `Components` in the runtime module. The probe must then compile the runtime.
- **Q9, the runtime's version pin.** **Decided: as recommended.**
  - **Recommendation:** an optional `runtime:` entry. Without it, the Builder uses the runtime release that matches its own version.
  - *Alternative:* a mandatory entry.
- **Q10, identity and `flagd version` (FR-034; UC-009 step 8; UC-011 BR-004; drop-in rule, D1).** **Decided: as recommended.** FR-034 asks `flagd version` to name the distribution, but any new or changed line changes what flagd-full prints today.
  - **Recommendation: keep today's output.**
    - `flagd version` prints exactly today's lines in every distribution: `flagd: <version> (<commit>), built at: <date>`, then the FIPS lines.
    - `<version>` and `<commit>` are the `-X main.version` and `-X main.commit` values. `make build-flagd` stamps `dev` and the short commit; the Dockerfiles stamp `${VERSION}` (flagd's release tag) and `${COMMIT}`, unchanged. The Builder stamps the manifest's `dist.version` and `git rev-parse --short HEAD` of the manifest's directory (else `unknown`), plus the date. UC-009 keeps flagd-full's `dist.version` equal to the release tag, so its output is identical to today's.
    - The identity is opt-in: `flagd version --verbose` adds `distribution: <name> <manifest version>` and `runtime: <R/runtime version from build info, or dev when replaced>`. `flagd components` (UC-011) shows the same.
    - Amend FR-034, UC-009 step 8 and UC-010 step 8 to name `flagd version --verbose`.
  - *Alternative:* add the `distribution:` line by default, as FR-034 reads today. That is a visible change for flagd-full, which would be tracked in #78.
- **Q11, manifests before any module is tagged.** **Decided by the project lead (changed from the recommendation): the OpenTelemetry Collector Builder's way.**
  - **Decision:**
    - Every entry carries a version. Repository manifests use the placeholder `v0.0.0` for relay modules, which their `replaces` lines make resolvable. A pseudo-version is equally valid.
    - The version check (step 7, BR-006) is relaxed for replaced modules, as A2 states.
    - The Builder also takes `--skip-strict-versioning`, as OCB does, which reports a resolved version that differs from the declared one as a warning instead of failing (A8). 7e amends BR-006 to name that flag.
    - The Builder's own A7 and A8 tests run against a file-based module proxy in `builder/testdata/proxy`, offline.
  - *Rejected:* pseudo-versions of merged commits without replaces. Those need network access and a merge.
- **Q12, who owns flagd-full's manifest.** **Decided: as recommended.**
  - **Recommendation:** UC-001 adds `distributions/flagd-full/manifest.yaml`. CI builds it, checks that the generated `components.go` equals the `flagd` module's, and reports NFR-008's duration. UC-009 makes it the release source.
  - *Alternative:* UC-009 writes it.
- **Q13, FIPS tags and platforms.** **Decided: as recommended.**
  - **Recommendation:** the default flags match today's release build: `CGO_ENABLED=0`, no `-trimpath`. `GOOS`, `GOARCH`, `GOFLAGS` and `GOFIPS140` pass through to the final build and are unset for the probe (Q5). There is no manifest section; FIPS and the platform matrix belong to UC-012 and UC-010.
  - *Alternative:* a `build:` section now.
- **Q14 (new), replacing relay modules that are not components.** **Decided by the project lead (changed from the recommendation): explicit `replaces`, no `local_root`.** Relay modules require each other at `v0.0.0-00010101000000-000000000000` and replace each other locally. A dependency's replaces don't apply to the generated main module, so it must replace every relay module in its build list (core, runtime, transport, sync builder), not only the components.
  - **Decision:**
    - Each repository manifest lists one `replaces` line per relay module in its build list, as OCB's `builder-config.yaml` does.
    - `replaces` paths are read relative to the manifest and written relative to `output_path`.
    - **The check:** `test/distributions` `TestRepositoryManifestsReplaceEveryRelayModule` runs in CI's `make test`. For each repository manifest it starts from the listed modules and the runtime, follows the `require` lines of their local `go.mod` files through the replace paths, and fails, naming the manifest and each `R/...` module that lacks a `replaces` line. It also fails on a `replaces` line whose path holds no `go.mod` with that module path (BR-007). Adding or splitting a module therefore fails CI at once, not later in a build.
    - When `go mod tidy` fails on a relay module at `v0.0.0-00010101000000-000000000000`, the Builder's A7 report adds the hint "missing `replaces` entry".
  - *Rejected:* a `local_root` key that derives the replaces from a directory scan.
- **Q15 (new; the blocker), how operator settings reach a component without the runtime knowing its type.** **Decided: as recommended.** On #71 the runtime maps flagd-full's flags into each official endpoint's Go settings types.
  - **Recommendation:** settings travel as plain data.
    - `runtime/cmd` keeps every flagd-full flag, config key and environment variable (pin 1b). It maps each one to a component type and a documented key, through a table in `runtime/cmd`. For example, `--ofrep-port` maps to `ofrep`/`port`.
    - The runtime hands each factory `Settings.Config` for its type: a `map[string]any` of plain values (numbers, strings, string lists, durations as strings).
    - Each endpoint factory decodes its own map. Telemetry objects (recorder, ConnectRPC options) come from `Settings.Telemetry` (T4), never from `Config`.
    - The runtime holds no endpoint, evaluator or format type.
    - The table records whether each value was set explicitly (viper's `IsSet`). The runtime ignores settings of absent components, so an OFREP-only distribution started with flagd-full's defaults (`--port`, `--sync-port`) starts normally (N3).
    - The table also tells UC-010 which component a setting belongs to. UC-010 BR-001 then stops startup only on an *explicitly set* setting of an absent component.
  - *Alternative:* each factory declares its own flags (name, environment variable, default), and `runtime/cmd` registers only those of present components. That is cleaner for extensions, but it moves flagd-full's CLI definition into the endpoint modules: a larger change to pin 1b's surface, and extension settings would arrive before UC-021 has specified them.

  - **Decision (project lead), operator settings for a distribution with its own `cmd`:** the `cmd` package owns the flags, configuration keys and environment variables of its distribution and builds `Components` and the plain-data settings of its components itself; the table of this question is flagd's `runtime/cmd` alone.

## 6. Risks

- **C-003 and the drop-in rule.** Section 0a: flags, config keys, environment variables, help text, startup failures, exit codes, `version` output, ports and effective endpoint settings are pinned (1a, 1b, 1e, 1f), and so is the module set (1c). There is no visible change for flagd-full.
- **C-003, settings as maps (Q15).** A key typo or a type change would silently drop a setting. Each factory rejects unknown keys, naming them, and 1e compares effective settings end to end.
- **C-004.** Every `github.com/open-feature/flagd/flagd/pkg/...` path moves; the list goes to UC-015. The `flagd` module path stays.
- **Workspace leakage and replaces.** `GOWORK=off` on every `go` call (`TestBuildIgnoresWorkspace`). Each repository manifest replaces every relay module explicitly, and `TestRepositoryManifestsReplaceEveryRelayModule` fails CI when a module is added or split without updating them (Q14).
- **Network in CI.** Builder unit tests use the file proxy; the end-to-end job uses the module cache.
- **The probe's cost.** Host build with the final flags shares most of the cache; it is part of NFR-008's measurement.
- **Stack churn.** PR 5 rewrites files that #71 and step 6 T4, M3 and E3 touch. It merges their branches in as they appear; the merge-up rule in `CLAUDE.md` handles later parent heads.
- **NFR-005, NFR-006.** `core/pkg/distribution` holds data over core types only. The evaluator is untouched apart from the moved helper (5b), which stays inside `evaluator/flagd`'s existing boundary row.
- **C-005.** No protobuf change. **C-006** is a preference: the builder module and PR 3 are upstream-shaped.
- **Over-building.** No standard manifests (UC-010), releases (UC-012), images (UC-002), `components` command (UC-011), per-component flag declaration (Q15's alternative) or build section (Q13).
