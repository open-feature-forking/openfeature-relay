## Findings

### 1. major: neither PR 1's candidate nor the integration suite is the Builder-built binary

- **Plan step:** base paragraph ("PR 1 … runs it with the Builder-built flagd-full from #96 as the candidate"), 1a ("the candidate (an image from `flagd/build.Dockerfile` on this branch)"), NFR-007 and BR-004 rows, 4a.
- **Evidence:**
  - `flagd/build.Dockerfile` on #96's branch compiles `flagd/main.go` (`go build … -o /bin/flagd-build flagd/main.go`). That `main.go` is the hand-written one: it calls `components.Official()` and sets `Telemetry = otelprovider.NewFactory()` itself.
  - The Builder's output goes to `distributions/flagd-full/build` (manifest `output_path: ./build`), and only `make build-flagd-full` uses it: `FLAGD_BINARY=…/distributions/flagd-full/build/flagd go test -run "TestCLICharacterization|TestStartupLogCharacterization"`, Makefile:297-303.
  - The integration suite builds its flagd image with `docker buildx build -f flagd/build.Dockerfile` (test/integration/integration_test.go:89-112) and runs the test-harness against it, on main and on #96 alike.
  - So until PR 3 (Q2) lands, the differential and the test-harness suites run against the hand-written build, not the Builder's. PR 1 being "green against #96" proves nothing about Builder output.
- **Fix:** either
  - (a) reorder: PR 2 → PR 3 → PR 1, so the differential's candidate image comes from the generated `flagd/`; or
  - (b) PR 1 builds its candidate from the Builder's binary in `distributions/flagd-full/build`, using the Dockerfile's final stage.

  Either way, say in the coverage table that NFR-007 and BR-004 hold only from PR 3 (or 4a) on.

### 2. major: the Builder writes more into `flagd/` than 2b allows, and it doesn't write `inventory.go`

- **Plan step:** Q2 ("The Builder regenerates `flagd/main.go` and `flagd/components/{components,inventory}.go`. It touches nothing else there"), 2b, 3a.
- **Evidence:**
  - **The generated files** are `go.mod`, `main.go`, `components/components.go` and `probe/main.go` (builder/internal/generate/templates.go:34-37). `Write` writes all of them to `output_path` (generate.go:158-172), and the build then runs `go mod tidy` there (gotool.go:126-151).
  - **`go.mod`:** with `output_path: ../../flagd`, it replaces `flagd/go.mod` with a generated one (header `// Code generated by relay-builder; DO NOT EDIT.`, only the manifest's requires and replaces), and tidy rewrites `go.sum`.
  - **`probe/main.go`:** it adds a `flagd/probe` package.
  - **`Inventory()`:** the generated `components.go` defines `Inventory()` itself (templates.go:131-133). The hand-written `flagd/components/inventory.go` declares it too, so keeping "every other file" yields a duplicate declaration and a compile error.
- **Fix:**
  - 2b names the real set.
  - Decide whether `flagd/go.mod` becomes generated (then today's `flagd/go.mod` contents must come from the manifest) or stays hand-kept (then the Builder needs a mode that leaves `go.mod` and skips tidy).
  - Delete `inventory.go` and `inventory_test.go` in 3a.
  - Keep `probe/` out of `flagd/`: a temp directory or an excluded path.

### 3. major: the generated package exports `Components()`, not `Official()`, and the runtime module's tests call `Official()`

- **Plan step:** risk C-004 ("Their exported names are unchanged, because the generated package keeps them"), 3a.
- **Evidence:**
  - **The two names:** the template's `main.go` calls `components.Components()` (templates.go:79), while hand-written `flagd/main.go:22` calls `components.Official()`.

    - `runtime/components_test.go:62`

    The last one is a UC-001 characterization pin.
  - So regenerating `flagd/components` breaks the runtime module's tests and changes a pinned test file.
- **Fix:**

  - Record in #89 which name survives.

### 4. major: `go install github.com/open-feature/flagd/flagd@<v>` already fails, and the proof the plan names doesn't test it

- **Plan step:** drop-in table row "`go install …@<v>` and the binary's build info … Proven by `go version -m` in `release-dry-run`"; Q2's rationale.
- **Evidence:**
  - `flagd/go.mod` on #96's branch has 17 `replace` directives (`git show …:flagd/go.mod | grep -c '=>'` → 17). `go install pkg@version` refuses a module whose `go.mod` contains replace directives. Keeping the `flagd` module path therefore doesn't keep `go install` working.
  - It already doesn't work, since UC-014's local replaces (Q7 there).
  - `go version -m` checks the binary's build info only; it never runs `go install`.
- **Fix:**
  - Move `go install` out of "stays identical". It is a known break until UC-012 publishes the modules and drops the replaces.
  - List it in the migration notes and in `accepted.yaml`, citing UC-012, since it isn't a #78 item. Or raise it to the project lead as a drop-in question.
  - Q2's case for keeping the `flagd` module then rests on build info, SBOM main component and the Dockerfiles, not on `go install`.
